# DosiRock iOS

> 냉장고 속 재료로 준비하는 일주일 도시락, `도시의 돌멩이` iOS 레포지토리

<br>

## 서비스 소개

도시의 돌멩이는 냉장고에 있는 재료와 먹고 싶은 재료를 바탕으로,  
직장인의 월요일부터 금요일까지 도시락 한 끼 구성을 제안하는 서비스

먼저 사용할 재료를 반영한 AI 주간 메뉴 추천부터 상세 레시피,  
부족 재료 확인과 조리 완료 후 재고 관리까지 연결

### 이번 주 레시피 (AI Recipe)

냉장고 재료와 사용자 조건을 기반으로 한 주간 도시락 구성 및 AI 레시피 제공

### 냉장고 (Refrigerator)

재료별 보유량 및 보유 여부와 권장 사용일 관리

### 마이페이지 (My Page)

사용자 프로필·설정 관리, 도시락 준비 현황 및 기타 정보 확인

<br>

## 기술 스택

* Language: Swift
* UI: SwiftUI
* Architecture: MVVM
* Networking: URLSession, async/await
* Serialization: Codable
* Test: XCTest
* IDE / Build: Xcode
* Backend: Java · Spring Boot, 별도 레포지토리 관리

<br>

## 프로젝트 구조

### 아키텍처

**기능별 폴더 구조와 MVVM 아키텍처 적용**

기능 단위로 폴더를 구성하고, 화면 표현·상태 관리·API 통신 책임 분리

| 구성 요소 | 역할 |
|---|---|
| `View` | 화면 구성, 사용자 입력 및 화면 상태 표시 |
| `ViewModel` | 사용자 동작 처리, 화면 상태 관리 및 Service 호출 |
| `Model` | 화면과 기능에서 사용하는 데이터 구조 |
| `Service` | 기능별 API 요청 및 응답 데이터 처리 |
| `Networking` | 공통 HTTP 요청, JSON 변환 및 네트워크 오류 처리 |

### 설계 원칙

* View의 직접적인 네트워크 호출 제외
* ViewModel을 통한 화면 상태 및 사용자 동작 관리
* 기능별 Service와 공통 네트워크 처리 분리
* 재사용 가능한 UI의 공통 컴포넌트 분리
* 색상·글꼴·간격 등 디자인 시스템의 공통 관리
* AI 생성·재고 차감·가격 계산 등 핵심 비즈니스 로직의 백엔드 처리
* 서버 응답을 기준으로 한 화면 갱신

### 폴더 구성

```text
DosiRock
│

│   └── RootView.swift

│   ├── AIRecipe                # 이번 주 레시피

├── Core
```

```text

```

## 주요 기능

### 이번 주 레시피 (AI Recipe)

**냉장고 재료를 활용한 월~금 1인분 도시락 구성**

* 먼저 사용할 재료 선택
* 이번 주 먹고 싶은 재료 선택
* 국물 메뉴 포함 여부 설정
* 사용자 조건을 반영한 AI 주간 메뉴 요청 및 결과 표시
* 한그릇형·반찬형·국물 포함형의 한 끼 구성 표시
* 밥을 제외한 하루 1~3개 요리 제안
* 월~금 요일 선택 및 날짜별 도시락 구성 조회
* 선택한 요일의 한 끼 구성 교체
* 주간 전체 부족 재료 목록 확인
* 주간 계획 확정
* 매주 토요일 00:00, 한국 시간 기준으로 제공되는 다음 주 추천 반영
* 이전 주 계획 조회

**메뉴별 AI 상세 레시피**

* 메뉴 선택 시 상세 레시피 생성 요청
* 재료별 필요량·보유량·부족량 및 조리 순서 표시
* 생성된 레시피 재조회
* 생성 중·완료·실패 상태 표시
* 생성 실패 시 재시도 제공

**조리 완료 및 재고 반영**

* 실제 조리 완료 요청
* 사용 재료 및 재고 부족 상태 확인
* 처리 완료 후 냉장고 보유량과 도시락 통계 갱신
* 처리 중 버튼 비활성화를 통한 중복 요청 방지
* 실패 시 기존 화면 상태 유지 및 재시도 제공

### 냉장고 (Refrigerator)

**재료 특성에 따른 보유 정보 관리**

* 서비스 재료 목록 검색 및 선택
* 수량 관리 재료의 보유량 등록·추가·수정
* 기본 재료의 보유 여부 전환
* 권장 사용일이 가까운 재료 안내
* 냉장고 재료 삭제
* 저장 결과의 목록 및 관련 화면 반영
* 빈 냉장고·검색 결과 없음 상태의 안내와 다음 동작 제공

### 마이페이지 (My Page)

**사용자 정보와 도시락 준비 현황 확인**

* 사용자 프로필 조회 및 수정
* 외식 한 끼 기준 비용 설정
* 도시락 준비 횟수 확인
* 외식 기준 비용과 도시락 재료비를 비교한 예상 절약액 확인
* 앱 정보 및 가격 데이터 안내

## 화면 구성 및 상태 처리

### 내비게이션

* 하단 탭: 이번 주 / 냉장고 / 마이페이지
* 탭별 화면 이동 상태 관리
* 상세 화면의 이전 화면 복귀
* 재료 등록·수정 등 입력 화면의 시트 제공
* 저장하지 않은 입력값이 있는 경우 이탈 확인

### 공통 상태

| 상태 | 처리 |
|---|---|
| 로딩 | 로딩 표시 및 중복 요청 방지 |
| 빈 결과 | 상태 설명과 재료 등록·조건 변경 등 다음 동작 제공 |
| 조회 실패 | 오류 안내 및 재시도 제공 |
| 저장 중 | 진행 상태 표시 및 중복 제출 방지 |
| 저장 실패 | 입력값 유지 및 재시도 제공 |
| 저장 성공 | 관련 화면 갱신 및 완료 안내 |
| 가격 정보 없음 | 미산정 표시, 임의 `0원` 표시 제외 |
| 과거 가격 사용 | 서버가 제공한 실제 조사일 및 안내 표시 |

## API 연동

### 통신 기준

* 백엔드 REST API와 JSON 형식으로 통신
* URLSession과 async/await 기반 비동기 요청

* 서버의 재료 ID를 기준으로 냉장고·레시피·가격 데이터 연결

* 앱 진입 및 필요한 화면 갱신 시 서버의 최신 상태 확인

## 브랜치 전략

`main`·`dev`·작업 브랜치 기반 운영

| 브랜치 | 역할 |
|---|---|
| `main` | 배포 가능한 안정 브랜치 |
| `dev` | 기능 통합 및 백엔드 연동 확인 브랜치 |
| `feat/{기능}-{이슈번호}-{작업명}` | 기능 개발 |
| `fix/{기능}-{이슈번호}-{작업명}` | 버그 수정 |
| `refactor/{기능}-{이슈번호}-{작업명}` | 리팩토링 |
| `test/{기능}-{이슈번호}-{작업명}` | 테스트 작업 |
| `chore/{설명}` | 빌드 및 설정 변경 |
| `docs/{설명}` | 문서 수정 |

이슈 번호가 없는 작업은 번호 생략

### 예시

```text
feat/recipe-3-weekday-selector
feat/refrigerator-8-add-ingredient
fix/recipe-15-duplicate-request

chore/init-ios-project
docs/readme-update
```

### 작업 흐름

1. 주요 기능·버그 단위의 **Issue** 생성
2. 최신 `dev`에서 작업 브랜치 분기
3. 구현 및 관련 빌드·테스트 확인
4. 작업 브랜치 → `dev` **PR** 생성
5. 셀프 리뷰 후 직접 병합 및 작업 브랜치 삭제
6. `dev`에서 기능 통합 및 백엔드 연동 확인
7. 배포 가능한 상태에서 `dev` → `main` PR 생성 및 병합

* `main` 직접 작업 제외
* 각 저장소 담당자 1인 기준 운영
* 필수 리뷰어 및 승인 인원 제한 미적용
* API 연동에 영향을 주는 작업은 상대 담당자에게 공유
* 연동 검토가 필요한 작업은 상대 담당자에게 리뷰 요청

## 커밋 컨벤션

```text
type: 제목 (#이슈번호)

본문 (선택): 무엇을, 왜 변경했는지 설명
```

* 하나의 커밋에 하나의 논리적인 변경 단위 반영
* 이슈가 있는 작업에만 이슈 번호 표기
* 제목은 변경 내용을 파악할 수 있도록 간결하게 작성

### 커밋 타입

| Type | 설명 | 예시 |
|---|---|---|
| `feat` | 새로운 기능 추가 | `feat: 주간 도시락 요일 선택 화면 추가 (#3)` |
| `fix` | 버그 수정 | `fix: 레시피 중복 생성 요청 수정 (#15)` |
| `refactor` | 동작 변경 없는 코드 구조 개선 | `refactor: 공통 네트워크 처리 분리` |
| `docs` | 문서 수정 | `docs: README 업데이트` |
| `style` | 포맷·들여쓰기 등 코드 스타일 정리 | `style: Swift 코드 포맷 정리` |
| `test` | 테스트 추가 및 수정 | `test: 추천 조건 ViewModel 테스트 추가` |
| `chore` | 빌드·의존성·환경 설정 변경 | `chore: 개발 환경 설정 추가` |
| `revert` | 이전 커밋 되돌리기 | `revert: 메뉴 교체 처리 변경 되돌림` |

UI 디자인·동작 변경은 변경 목적에 따라 `feat`·`fix` 등으로 구분, `style`은 코드 포맷 정리에 사용

### 예시

```text
feat: 요일별 도시락 구성 조회 화면 추가 (#3)

월~금 목록을 요일 선택 방식으로 변경하여 하루 구성을 확인하도록 구현

- 요일별 날짜 및 선택 상태 표시
- 선택한 요일의 메뉴 카드 표시
- 요일 전환 시 기존 추천 결과 유지
```

## Issue / PR 규칙

### Issue

```text
[Tag] 제목
```

* 주요 기능·버그·리팩토링 단위로 생성
* Labels 및 담당자 지정
* 작업 목적 / 상세 내용 / 체크리스트 / 참고 사항 포함
* 단순 오타·문서 수정 등 작은 작업은 Issue 생략 가능

### PR

```text
[Tag] 제목
```

* 기능 개발 PR의 대상 브랜치: `dev`
* 배포 반영 PR의 대상 브랜치: `main`
* Labels 및 담당자 지정
* 관련 이슈 / 변경 목적 / 작업 내용 / 확인 결과 포함
* UI 변경 시 스크린샷 또는 동작 영상 첨부
* 관련 이슈가 있으면 `Closes #번호` 연결
* 셀프 리뷰 및 빌드·관련 테스트 확인 후 직접 병합
* Reviewer는 검토가 필요한 경우에만 지정

### 셀프 리뷰 기준

* 작업 목적과 관계없는 변경의 포함 여부
